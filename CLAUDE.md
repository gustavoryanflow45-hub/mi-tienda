# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Multi-vendor e-commerce marketplace built with Laravel 12. Sellers register shops, list products, and receive payments. Customers browse, cart, and checkout. Payment gateway is auto-selected by geolocation: PayPhone for Ecuador, Stripe everywhere else.

## Commands

```bash
# First-time setup
composer run setup           # install deps, key:generate, migrate, npm build

# Development (runs all services concurrently)
composer run dev             # artisan serve + queue:listen + pail + npm run dev

# Individual services
php artisan serve            # HTTP server on :8000
php artisan queue:listen     # Background job worker
npm run dev                  # Vite HMR dev mode
npm run build                # Production asset build

# Testing
composer run test            # config:clear then phpunit
php artisan test --filter=OrderTest   # single test class

# Code style
./vendor/bin/pint            # format PHP files
```

## Architecture

### Request Flow

Routes → Controllers → Services/Models → Blade views (`resources/views/`). Three route files, one per area, each with its own controllers namespace:

| Area | Routes | Controllers | Gate |
|---|---|---|---|
| Storefront (customers, public pages, cart, checkout, `/dashboard`, `/orders`, `/wallet`, public shop registration) | `routes/web.php` | `App\Http\Controllers\Shop\` (+ `Auth\`, `Payments\`, and `Seller\RegistrationController` for `/shops/create`) | `web` guard |
| Seller panel, everything under `/seller` | `routes/seller.php`, registered in `bootstrap/app.php` with `auth` + `shop.approved` + `seller`, prefix `/seller`, names `seller.*` | `App\Http\Controllers\Seller\` | `web` guard, approved shop |
| Admin panel | `routes/admin.php` (see **Admin Access Separation**) | `App\Http\Controllers\Admin\` | `admin` guard + 2FA |

Only `Controller` and `LanguageController` (used by the storefront and the panel) stay in the root namespace. **Every seller action lives in `routes/seller.php`**: publishing/unpublishing (`seller.products.toggle-published`, formerly on `HomeController`) and sending to the warehouse (`POST /seller/orders/{id}/send-to-warehouse`, formerly `/orders/{id}/…`) used to sit outside `/seller`, so a seller whose shop had been **rejected** could still do both. The `seller` alias is `EnsureUserIsSeller` (role only; it runs after `shop.approved`, which already sends shopless users to `/dashboard`). `tests/Feature/SellerRoutesTest.php` fails if a `/seller` route lacks any of the three middleware or a controller sits in the wrong namespace.

No API layer — all responses are server-rendered Blade. AJAX calls (search autocomplete, mini-cart modal, variant prices) return HTML partials or JSON from the same controllers.

`app/Helpers/helpers.php` is autoloaded via composer.json; it defines global helpers like `uploaded_asset($path)` (resolves uploaded file paths, falls back to a placeholder image).

### User Types

`users.user_type` distinguishes `customer` and `seller` (and the legacy `admin`, see below). The storefront's `User` model handles them. **Panel admins are not users**: they live in the `admins` table (`App\Models\Admin`) and authenticate with the separate `admin` guard — see **Admin Access Separation**. The rows that still carry `user_type = 'admin'` in `users` were copied to `admins` (same id, `admins.legacy_user_id`) and kept; they no longer open the panel and have **no special power in the storefront**: `User::isAdmin()` no longer exists, nothing in the shop checks `user_type = 'admin'`, so such a row behaves like a customer (`OwnershipPolicyTest`, `SellerShopApprovalTest`). Sellers also have a `shops` record. Shop registration (`/shops/create`) is public and creates the user with `user_type = 'seller'`.

Four middleware aliases are registered in `bootstrap/app.php` (`seller` is described under **Request Flow**, `admin.2fa` under **Admin Access Separation**):
- **`admin`** (`EnsureUserIsAdmin`) — guards the whole admin panel (`/admin/*`, warehouse included), together with `auth:admin` and `admin.2fa`: it requires an `Admin` on the `admin` guard. Always place it after `auth:admin` so guests get redirected to the login instead of a 403, and never use plain `auth` on a panel route (`AdminAccessTest` checks both on every route). See **Admin Access Separation** below.
- **`shop.approved`** (`EnsureShopApproved`) — guards every `/seller/*` route (the whole `routes/seller.php`). Because `/shops/create` is public and logs the user straight in, `user_type = 'seller'` alone means nothing: the shop must also have `status = 1`. Nobody bypasses it (panel accounts are another table and never use `/seller`); pending/rejected/shopless sellers are redirected to `/dashboard` with a `warning` flash.

Admins approve shops at `/admin/shops` (`Admin\ShopController`, view `admin/shops.blade.php`) — list with status/search filters, ID document thumbnails, and approve/reject actions. `shops.status`: `0` pending, `1` approved, `2` rejected (`Shop::statusLabel()`); the constants live on `Admin\ShopController`. The panel nav (`layouts/admin`) shows the pending-count badge.

Each decision sends `ShopStatusUpdatedNotification` to the seller on **both** `database` and `mail` (a decision can take days, so the seller may not be logged in). A no-op re-approval sends nothing. `DashboardController` reads the unread ones, marks them read, and passes `$shopUpdates` to both dashboard views, which render `partials/shop-status-banner.blade.php` — same read-once pattern as `OrderStatusUpdatedNotification` in `/orders`. Its `toMail()` calls `route()`, which is safe in console and queue contexts (the console kernel's `SetRequestForConsole` bootstrapper builds a request from `APP_URL`). It only breaks in ad-hoc scripts that boot the **HTTP** kernel without binding a `request` — `url()` fails there too, so swapping helpers is not a fix; bind a request instead.

Controllers additionally check `$user->isSeller()` in a constructor middleware closure (`Seller\ProductController`, `Seller\OrderController`); the `Admin\*` controllers repeat `auth:admin` + `admin`. These are defense in depth — the route middleware is the real gate for roles, and **ownership** is decided by the policies in `app/Policies` (auto-discovered): `ProductPolicy` (`update`: owner via `added_by`, or a panel `Admin`; `togglePublished`: the owner only; `moderate`: `Admin` only), `OrderPolicy` (`view`: buyer, a seller with a line in the order, or a panel `Admin`; `confirm` / `sendToWarehouse`: a seller with a line — denials are `denyAsNotFound()`, i.e. 404, so another seller's order id is not confirmed to exist), `OrderDetailPolicy` (lines belong to `seller_id`) and `ShopPolicy` (`approve`/`reject` `Admin` only). Every policy method takes `User|Admin`: the panel authorizes with the same policies (inside `auth:admin` the `Admin` is the Gate user), and a storefront `User` gets `false`, never a `TypeError`. Controllers call `$this->authorize()` (`Seller\ProductController@togglePublished` uses `Gate::denies` to keep its JSON 403). Lists still filter by `added_by` / `seller_id` in the query — a policy does not filter collections. Covered by `tests/Feature/OwnershipPolicyTest.php`.

`User::$fillable` deliberately **excludes** `user_type`, `balance`, `banned`, `email_verified` and `verification_code`. Assign them explicitly (`$user->user_type = ...`), never through `create()`/`fill()` with request data — see `RegisterController` and `Seller\RegistrationController`. Model factories bypass this via `Model::unguarded()`, so tests can still set them inline.

Flash messages (`success` / `warning` / `error`) render globally via `partials/flash.blade.php`, included in the app layout.

### Email Verification

`users` carries both `email_verified_at` and a legacy `email_verified` flag; `User::isVerified()` accepts either — always use it rather than checking the columns directly.

`VerifyEmailNotification` (mail channel) is sent on customer registration (`RegisterController`) and shop registration (`Seller\RegistrationController`). It builds a **temporary signed URL** to `verification.verify` (`URL::temporarySignedRoute`, 60 min — `VerifyEmailNotification::EXPIRES_MINUTES`), so no token is persisted; the legacy `verification_code` column is unused and merely cleared on success.

Routes (`Auth\VerificationController`): `GET /email/verify` (`verification.notice`, auth) is the "check your inbox" page; `GET /email/verify/{id}/{hash}` (`verification.verify`) is `signed` but deliberately **not** `auth` — the link is opened from an email, often in a browser with no session, and it logs the user in on success; `POST /email/resend` is `auth` + `throttle:6,1`. The `{hash}` is `sha1($user->email)`, so changing the email invalidates outstanding links.

`Seller\ProductController` bounces unverified sellers to `verification.notice`. `MAIL_MAILER=log` locally — verification emails land in `storage/logs/laravel.log`, not a real inbox.

### Password Reset

`Auth\PasswordResetController` runs Laravel's password broker (`Password::sendResetLink` / `Password::reset`; token in `password_reset_tokens`, 60-minute expiry and 60-second resend throttle from `config/auth.php`). Routes, all under `guest`: `GET /password/reset` (`password.request`), `POST /password/email` (`password.email`, `throttle:6,1`), `GET /password/reset/{token}` (`password.reset`, view `auth/passwords/reset.blade.php`), `POST /password/reset` (`password.update`, `throttle:6,1`) — on success the user is logged in and sent to `/dashboard`. `POST /password/email` answers the same "if that account exists…" line whether or not the email is registered, so it cannot be used to enumerate users; only `RESET_THROTTLED` is surfaced. The mail is `ResetPasswordNotification`, which extends Laravel's `ResetPassword` (same token) and only rewrites the text in Spanish; `User::sendPasswordResetNotification()` routes to it. Broker status strings live in `lang/es|en/passwords.php`. Covered by `tests/Feature/PasswordResetTest.php`.

`app/Http/Middleware/SetLocale.php` runs on every `web` request and applies `session('locale')` (see Localization below).

### Admin Access Separation

The admin panel — shops, settlements, admin wallet and warehouse — lives in its own file, `routes/admin.php`, registered by `App\Support\AdminRoutes::register()` (called from `bootstrap/app.php`'s `then:`; tests that change `config('admin.*')` call it again) inside the `web` group with the name prefix `admin.` and the path prefix `ADMIN_PATH` (default `admin`), so a bug in the shop or the seller panel does not reach it. Its controllers are all in `App\Http\Controllers\Admin\` and `routes/web.php` references none of them (`AdminAccessTest` checks both). Every panel route is named `admin.*`: the warehouse is `admin.warehouse.*` and the wallet review `admin.wallet.approve|reject|withdrawal.*`. `config/admin.php` drives it (`.env.example` documents the variables):

- **`ADMIN_DOMAIN`** set (production): the group gets `Route::domain()`, so admin URLs exist only on that host (`admin.example.com/admin/shops`) and are 404 on the shop's host; `route()` builds absolute URLs to it. Empty (XAMPP, tests): same host, `/admin/...`. `ADMIN_PATH` moves the whole panel (`/gestion/...`); with a domain it may be empty (`admin.example.com/shops`), without one an empty value falls back to `admin` so the panel never sits on `/`. Changing the domain or the path needs `config:clear` **and** `route:clear` — `route:cache` bakes it in.
- **`IsolateAdminHost`** (prepended to `web`, so it runs before `StartSession`): on the admin host the session uses its own cookie (`ADMIN_SESSION_COOKIE`), host-only and `SameSite=strict`, so even a wrong `SESSION_DOMAIN=.example.com` cannot share the admin session with the shop. Keep `SESSION_DOMAIN` empty and `SESSION_SECURE_COOKIE=true` in production. Only panel routes answer on the admin host: a GET to a shop route (an old bookmark) redirects to `APP_URL`, any other verb is 404. The panel switches language through its own `POST /admin/language` (`admin.language`, the same `LanguageController`), because the locale lives in the panel session. Without a domain (XAMPP) the `admin.*` routes use that same separate cookie, with `path=/ADMIN_PATH`: the browser never sends it to the shop, so logging out of one does not log out the other. The middleware switches the cookie name on the session `Store` and the config only for the request and restores both afterwards — the `SessionManager` caches the `Store` with its name, and a process that serves several requests (tests, Octane) must not hand the panel cookie to the shop.
- **`ADMIN_ENFORCE_HOST=true`**: `EnsureUserIsAdmin` also answers 404 to admin requests not arriving through `ADMIN_DOMAIN` — and with no domain configured it closes the panel (fails closed).
- **Guard `admin`** (`config/auth.php`: session driver, provider `admins` → `App\Models\Admin`). A storefront session or (future) token is a guest for it, so a customer, a seller or a `users` row with `user_type = 'admin'` hitting a panel URL is redirected to the panel login — not a 403. The panel routes use `auth:admin` (which makes `admin` the default guard for the request, so `$request->user()` / `Auth::user()` are the `Admin` there) plus `auth.session`, which logs out the admin's other sessions when the password changes. Inside the panel prefer explicit `Auth::guard('admin')` / `$request->user('admin')`.
- The panel has its own login, `/admin/login` (`Admin\LoginController`, `Auth::guard('admin')->attempt()`): only the `admins` table is searched, the same generic error for any other account, no "remember me"; it stamps `admins.last_login_at`. There is no password reset by email: accounts are created with `php artisan admin:create {email} --name=` and change password with `php artisan admin:password {email}`, both asking twice and enforcing `Admin::passwordRule()` (12+ chars, mixed case, numbers, symbols). `bootstrap/app.php`'s `redirectGuestsTo` sends guests on any `admin.*` route there instead of `/login`. **Views.** Every panel view lives in `resources/views/admin/` and extends **`layouts/admin.blade.php`**, which depends on nothing from the storefront layout (no header, cart, search, footer or `partials/flash`; only the theme CSS, `vendors.js` and `noindex`), so the panel can be lifted out with that folder and that file. The only storefront partials still shared are presentational ones (`order-items-cell`, `variant-badge` on the warehouse page). The top bar carries the sections, the admin's name, language and logout; `App\View\Composers\AdminNavComposer` (registered in `AppServiceProvider`) feeds it `$adminNav` — the admin, whether 2FA was passed (before that only logout shows) and the pending-shop and warehouse-arrival counts. Flashes come from `admin/partials/flash`; a view that renders its own alerts declares `@section('flash_in_page', '1')` (shops, settlements, wallet) so they do not show twice, as they did under `layouts.app`. **The storefront never links to the panel**: the seller dashboard and `/seller/orders` sidebars lost their admin entries (and the `dashboard.nav.warehouse|settlements|shop_approvals` keys). `tests/Feature/AdminLayoutTest.php` fails if a storefront view calls `route('admin.…')` or a panel view extends `layouts.app` or a storefront chrome partial.

**Two-factor (TOTP).** `pragmarx/google2fa` + `bacon/bacon-qr-code`, used directly — not `google2fa-laravel`, whose middleware reads the secret from a `users` column. Enrollment lives in `admin_two_factors` (`AdminTwoFactor`, keyed by `admin_id`, `Admin::twoFactor()`): `secret` with the `encrypted` cast (rotating `APP_KEY` means re-enrolling everyone), `recovery_codes` as bcrypt hashes (8, shown once, `Cache-Control: no-store`), `last_used_timestep` so a code cannot be replayed. Moving the admins out of `users` kept the row and its encrypted secret, so nobody had to re-enroll. **Passing** 2FA is stored in the session only — `EnsureAdminTwoFactor` (alias `admin.2fa`) compares `session(EnsureAdminTwoFactor::SESSION_KEY)` with the admin id, so it dies with the session or the logout. `ADMIN_REQUIRE_2FA=false` disables the check.

Enrollment is **only** through `php artisan admin:2fa-invite {email}`, which prints a temporary signed link (30 min, `--minutes`) to `admin.two-factor.setup`; the page also requires being logged in as that admin. A stolen password alone can therefore never enroll an authenticator. That solves the first access too: an admin without 2FA cannot enter the panel and the challenge page tells them to ask for the link. `--reset` drops the current enrollment (lost phone, rotated key); without it the command refuses. Tests create admins with `Admin::factory()` and use `Tests\Concerns\PassesAdminTwoFactor::actingAsAdmin($admin)` (acts on the `admin` guard); plain `actingAs($admin, 'admin')` where the 2FA flow itself is under test. The flow itself is `tests/Feature/AdminTwoFactorTest.php`.

**Roles and permissions.** `spatie/laravel-permission` (v6) on the **`admin` guard only** (`Admin` uses `HasRoles` with `$guard_name = 'admin'`; storefront users have no roles). `App\Support\AdminPermissions` is the single definition: 12 permissions (`shops.view|decide`, `products.view|edit|moderate`, `orders.view`, `warehouse.view|operate`, `settlements.view|settle`, `wallet.view|decide`) and four roles — **super-admin** (every permission, assigned explicitly rather than through a `Gate::before`), **finanzas** (settlements and wallet, read the rest except the warehouse), **operaciones** (shops, products, orders, warehouse; no money) and **soporte** (read-only: every `.view`). One role per account. Every route in `routes/admin.php` after the 2FA carries `permission:<name>` (403 without it); policies check the same permission for an `Admin` (`ProductPolicy` `products.edit|moderate`, `ShopPolicy` `shops.view|decide`, `OrderPolicy`/`OrderDetailPolicy` `orders.view` or `warehouse.view`), and the views hide what the role cannot use — nav sections, counters (`AdminNavComposer`) and action buttons (`@can`), with "Solo lectura" where the buttons would be. `/admin` (`Admin\HomeController`) redirects to the first section the role can see, 403 for an account without a role.

Migrations `2026_11_05_100000_create_permission_tables` (spatie's) and `2026_11_05_100100_seed_admin_roles` (runs `AdminPermissions::sync()` and makes **every existing admin super-admin**, so nobody lost access). Accounts: `php artisan admin:create {email} --role=` (default **soporte**, least privilege), `php artisan admin:role {email} {role}` (replaces the role; refuses to demote the last super-admin; `--list` prints roles, permissions and accounts), `php artisan admin:roles-sync` after editing `AdminPermissions` (idempotent; it never deletes roles or permissions no longer listed). No UI grants roles, on purpose. `Admin::factory()` creates a super-admin unless `->role('soporte')` etc. Covered by `tests/Feature/AdminRolesTest.php`.

**IP allowlist.** `ADMIN_ALLOWED_IPS` (comma-separated IPs or CIDR ranges, `config('admin.allowed_ips')`): `RestrictAdminIp` answers 404 to any other address on every `admin.*` route, login included; empty means no restriction. It is the **first** middleware of the `web` group (prepended in `bootstrap/app.php`, before `IsolateAdminHost`, `StartSession` and `VerifyCsrfToken`): as a route middleware a blocked POST got a 419 from the CSRF check — revealing the route — and every attempt opened a session; now a blocked request gets a plain 404 and no cookie. It uses `$request->ip()`: behind nginx or Cloudflare declare them with `trustProxies` in `bootstrap/app.php`, or every request carries the proxy's IP — it deliberately does not read `CF-Connecting-IP`, which anyone can send when Cloudflare is not in front.

**Throttling.** Named limiters in `AppServiceProvider`: `admin-login` (5/min per email+IP, 20/min per IP) and `admin-2fa` (5/min per admin, on the challenge and the setup POST); exceeding them returns to the form with an error, not a blank 429. On top, 10 wrong codes in 15 minutes (`TwoFactorController::MAX_FAILURES` / `LOCKOUT_SECONDS`) log the admin out; the counter is per account, so logging in again does not reset it. The storefront password reset keeps its own `throttle:6,1`. Covered by `tests/Feature/AdminThrottleTest.php`.

**Audit log.** `App\Services\AuditLog::record($action, $subject, $meta)` writes to `admin_audit_logs` (`AdminAuditLog`, insert-only: the model throws on update and delete) the actor, action, polymorphic subject, `meta` JSON, IP, user agent and time. Despite the table name it is not admin-only: the actor (by default whoever is authenticated on the request's guard, or the `$actor` argument) goes to `admin_id` when it is an `Admin` and to `user_id` when it is a storefront `User` (a seller importing a CSV). Recorded:

| Action | Where | `meta` |
|---|---|---|
| `shop.approved` / `shop.rejected` | `Admin\ShopController` (not on a no-op) | `seller_id` |
| `seller.settled` | `Admin\SettlementController`, after `SettlementService::settle()` returns (the service itself is not touched) | gross, commission, net, lines |
| `wallet.recharge.approved` / `.rejected`, `wallet.withdrawal.approved` / `.rejected` | `Admin\WalletController` | `user_id`, `amount`, `fee` |
| `order.dispatched` / `order.delivered` | `OrderFulfillmentService` (from `Admin\WarehouseController`) — delivery is what makes a sale settleable | — |
| `product.approved` / `product.disabled` / `product.edited` | `ProductService::setApproved()` / `Admin\ProductController@update` | `seller_id` |
| `products.csv_imported` | `Seller\ProductController@bulkStore` (seller or admin) | `created`, `errors` counts |
| `admin.login` / `admin.login_failed` | `Admin\LoginController` (failed: no actor, attempted email) | `email` |
| `admin.2fa.passed` / `.failed` / `.recovery_used` / `.locked_out` / `.enrolled` | `Admin\TwoFactorController` | method / remaining codes |
| `admin.2fa.invited` / `admin.2fa.reset` | `admin:2fa-invite` (console: no actor, no IP) | `via`, `minutes` |
| `admin.created` / `admin.password_changed` | `admin:create` / `admin:password` (console: no actor, no IP; the subject is the `Admin`) | `via`, `role` |
| `admin.role_assigned` | `admin:role` | `via`, `role`, `previous` |

Never logged: card data, recharge proofs, bank account numbers, CSV contents, passwords, TOTP or recovery codes. `AuditLog` also drops any `meta` key matching `pass|secret|token|card|cvv|cvc|proof|otp|recovery|account_number|iban` as a safety net — pass explicit, harmless fields anyway. The entry is written after the action succeeds, outside its transaction. There is no UI to browse it yet. Covered by `tests/Feature/AuditLogTest.php`.

### Mobile API (`/api/v1`)

Laravel Sanctum 4, **tokens only** for the Flutter apps of customers and sellers. The contract for app developers is `docs/api/v1.md` (prose: error codes, token lifecycle, flows) plus **`docs/api/openapi.yaml`** (OpenAPI 3.1, hand-written, the machine reference for client generation); keep both in sync with any change. All sub-phases are done: 2a auth, 2b catalog, 2c cart/checkout/payments, 2d profile/orders/seller, 2e OpenAPI. **`tests/Feature/Api/V1/OpenApiSpecTest.php` enforces the spec**: every `api/v1` route (method + path) must be documented and nothing else; `security: []` exactly on routes without `auth:sanctum`; each operation's `x-abilities` must equal the route's `abilities:` middleware; every `$ref` resolves; and real responses from the main endpoints are validated against their schemas by a small built-in JSON Schema checker (type incl. `[x, 'null']`, required, properties, items, enum, const, allOf, oneOf, `$ref`). Adding or changing an endpoint therefore means editing the YAML in the same change. It is parsed with `symfony/yaml` (a direct `require-dev`). In inline YAML maps (`{ … }`) quote any `description` containing commas, colons or semicolons.

- **Routing**: `bootstrap/app.php` registers `routes/api.php` (prefix `/api`), which mounts `routes/api/v1.php` under `v1` with names `api.v1.*` and the middleware `SetApiLocale` (locale from `Accept-Language`, since the API has no session; it is in the priority list before `AuthenticatesRequests`, so even a 401 is localized) + `throttle:api`. A v2 goes next to it. Controllers in `App\Http\Controllers\Api\V1\`, Form Requests in `App\Http\Requests\Api\V1\`, Resources in `App\Http\Resources\V1\`.
- **Never the panel**: no API route uses `Admin\` controllers, `web`, `auth`, `admin*` or `permission:` middleware; `Admin` has no `HasApiTokens`; `config('sanctum.guard')` is `[]`, so neither a storefront nor a panel **session** authenticates `/api` — only a Bearer token. `tests/Feature/Api/V1/ApiRoutesTest.php` checks all of it.
- **Tokens per device** (`App\Services\ApiTokenService`): login takes `device_id` (stable UUID from the app) + `device_name`; `personal_access_tokens.device_id` (added in our migration `2026_11_06_100000_create_personal_access_tokens_table.php`) lets a new login from the same device replace its token. Each token gets `expires_at` = now + `API_TOKEN_TTL_DAYS` (30, `config/api.php`); `POST /auth/token/rotate` issues a fresh one (new expiry, abilities recalculated) and deletes the old; `API_MAX_DEVICES` (10) closes the least-used session when exceeded. `GET/DELETE /auth/devices[/{id}]` list and revoke sessions. Expired tokens are pruned daily (`routes/console.php` schedules `sanctum:prune-expired --hours=24`; needs `schedule:run` every minute — a Windows Task Scheduler job locally).
- **Abilities** (`App\Support\ApiAbilities`): customers get `profile:read|write`, `cart:write`, `checkout:write`, `orders:read`, `wallet:read|write`; a seller **with an approved shop** also `seller:products`, `seller:orders`. Routes use Sanctum's `abilities:` / `ability:` aliases. Abilities only refresh on rotation, so every `/seller` route also carries `api.seller` (`EnsureApiSellerShopApproved`, after the ability) which re-checks the approved shop on each request → `403 shop_not_approved`.
- **Who gets a token**: only verified (`User::isVerified()`), non-banned users. `register` creates the customer through `CustomerRegistrationService` (shared with the web `RegisterController`: `user_type` set there, never from input) and returns **no token**. `login` compares against a dummy bcrypt hash when the email does not exist, so timing and the body (`401 invalid_credentials`) are the same either way. `EnsureApiUserIsActive` (alias `api.active`, on every token route) revokes the token and answers `403 account_disabled` if the account is banned mid-session — the first place `users.banned` is enforced at all; the web login still ignores it. `email/resend` and `password/forgot` answer 202 with the same text whether or not the account exists (the reset text is `PasswordResetController::SENT_MESSAGE`).
- **Errors**: `App\Support\ApiExceptions` (registered in `withExceptions`) renders every exception under `/api/*` as `{message, code}` (+`errors` for validation), regardless of `Accept`: `validation_failed` 422, `unauthenticated` 401, `forbidden` 403, `not_found` 404, `method_not_allowed` 405, `too_many_requests` 429 (with `Retry-After`), `business_rule` 422 (any `BusinessRuleException` from the services), `http_error` otherwise; anything unexpected falls through to Laravel's JSON. Error responses also carry `Content-Language`.
- **Rate limits** (`AppServiceProvider::configureApiRateLimiting()`): `api` 60/min per user or IP; `api-auth` (register, login, resend, forgot) 5/min per email+IP and 20/min per IP.
- API register asks for 8+ characters with letters and numbers; the web form still accepts 6 — align it when convenient.

- **Catalog** (public, no token): `GET /home`, `/categories[/{slug}]`, `/brands`, `/products` (paginated, `ProductIndexRequest`: `q`, `category` slug incl. children, `brand`, price range, `featured`, `sort`, `per_page` ≤ 50) and `/products/{slug|id}` (`ProductDetailResource`: photos, plain-text description — the seller's HTML is stripped, `<script>`/`<style>` blocks included — shop, `variants.combinations` built from `Product::stockMap()` with the `variation` key the cart uses, related). Approving/rejecting has no API route at all (a test fails if one appears). Withdrawals expose only `account_last4`; recharge `approval` (0 / 1 / -1) is mapped to `pending|approved|rejected`. The amount must exceed the fee. `WALLET_MIN_WITHDRAWAL` must be set to its real value before production. `WalletRecharge::$fillable` now includes `network` and `transaction_id`: `requestRecharge()` always passed them, but they were silently dropped, so the panel's verification columns were always empty.

Listing does not mark them read, unlike the web pages. The list carries `meta.unread_count`.

- **Push sending (FCM HTTP v1, no SDK)**: `App\Notifications\Channels\FcmChannel` (put `FcmChannel::class` in `via()` and implement `toFcm(): FcmMessage`) is on `OrderStatusUpdatedNotification`, `SellerNewOrderNotification`, `SellerSettledNotification` and `ShopStatusUpdatedNotification`, only when the notifiable is a `User` (panel accounts never get push). The channel never calls Google in the request: it builds the message in the store's default locale (`services.fcm.locale` = `APP_LOCALE`; not `config('app.locale')`, which `app()->setLocale()` overwrites at runtime), adds `data.type` (`App\Support\NotificationTypes`, shared with the API's `NotificationResource`) and `data.notification_id` (the database row's id), and queues one `App\Jobs\SendPushNotification` per device token (3 tries, backoff 10/60/300 s) — **pushes need `queue:work` running**. `App\Services\Push\FcmClient` signs an RS256 JWT with the Firebase service account (`FCM_CREDENTIALS`, path to the JSON — keep it out of `public/` and git), exchanges it for an OAuth token cached until 5 min before expiry (re-fetched once on a 401), and POSTs `projects/{id}/messages:send`. `UNREGISTERED`, `SENDER_ID_MISMATCH`, 404 or an `INVALID_ARGUMENT` about the registration token → the token is removed from its session; any other error throws so the queue retries (a malformed message never deletes a token). Without credentials or with `FCM_ENABLED=false` the channel is a no-op and the database notification is still stored. The channel instance (and the client's cached credentials) lives as long as the process: after changing the credentials run `php artisan queue:restart`. ### Checkout & Payment Flow

This is the most intricate part of the app — read these files together before touching payments: `CheckoutController`, `CheckoutService`, `GeolocationService`, `Payments/StripeController`, `Payments/PayPhoneController`, `Services/Payments/PayPhoneService`, `Order::markPaid()`.

1. `GET /checkout` (`CheckoutController@index`) only renders: **no order exists yet**. The pending `Order` (status `pendiente`, `payment_status = 'unpaid'`) and its `OrderDetail` rows are created by `CheckoutService::pendingOrderFor()` when the buyer presses "Pagar" (Stripe intent / PayPhone prepare), and its id goes to `session('checkout_order_id')`; a later attempt reuses that order and resyncs totals and lines from the cart. Leaving the checkout without paying records nothing. `pendingOrderFor()` is the session wrapper around `syncPendingOrder($user, $reuse, $shipping)`, which the API calls with an explicit order and shipping.
2. Gateway selection: `GeolocationService::gatewayFor()` → `payphone` if country is EC, else `stripe`. Overridable per-request with `/checkout?gateway=stripe|payphone` (any other value, `kushki` included, falls back to the detected one); the payment card links to the other gateway. **On localhost (127.0.0.1/::1) the country resolves to EC in non-production**, so PayPhone is the default gateway in local dev. Country lookups (via `stevebauman/location`) are cached per-IP for 6 hours; the client IP honors the `CF-Connecting-IP` header. `checkout/index.blade.php` renders one panel or the other and only loads Stripe.js for Stripe.
3. Stripe: `POST /payments/stripe/intent` creates a PaymentIntent (via `app/Services/Payments/StripeService.php`) and Stripe Elements confirms it in the page. PayPhone (redirect "Botón de pagos", https://docs.payphone.app/boton-de-pago-por-redireccion): `POST /payments/payphone/prepare` calls `api/button/Prepare` and answers the URL to send the browser to — `payWithCard` or, with `method=app`, `payWithPayPhone`; the card is typed on PayPhone's page, never ours, and it must not be framed. Amounts go **in cents** and must add up: `amount = amountWithoutTax + amountWithTax + tax` (`PayPhoneService::amounts()`, see Tax). Each attempt gets a fresh `clientTransactionId` = `GS{orderId}-{10 chars}` (PayPhone wants it unique; the order id is read back from it). Both start routes carry `throttle:payments` (`AppServiceProvider`: 10/min per user and 30/min per IP, shared by the two gateways) so they cannot be used to test stolen cards in bulk; a hit returns JSON 429 with `message` (what the checkout shows) and `status`. Covered by `tests/Feature/PaymentThrottleTest.php`.
4. Confirmation. Stripe: `/webhooks/stripe` marks orders paid — but **webhooks never reach localhost**, so `CheckoutController@success` also verifies the PaymentIntent directly on the `?payment_intent=` redirect. Don't remove either path. PayPhone: there is no webhook; it redirects to `GET /payments/payphone/return?id=…&clientTransactionId=…`, and `PayPhoneController@handleReturn` **must** call `api/button/V2/Confirm` — **unconfirmed payments are reversed by PayPhone after 5 minutes**. That is why the route has neither `auth` nor a throttle: with a lost session it still confirms, then sends the buyer to log in with `orders.show` as the intended URL. It only marks paid on `statusCode` 3 (`STATUS_APPROVED`) when the confirmed `clientTransactionId` and `amount` match the order (a mismatch — the cart changed in another tab — is logged as critical and shown as "contact support"); `statusCode` 2 or a Confirm error leave it unpaid; an already-paid order is not confirmed twice. `/payments/payphone/cancel` is PayPhone's `cancellationUrl`. Covered by `tests/Feature/PayPhoneGatewayTest.php`.
5. `Order::markPaid($gateway, $reference)` is the single place an order becomes paid: it updates payment status, the lines, deducts stock and sends a database `SellerNewOrderNotification` to each seller involved; it is a no-op on a paid order. It does **not** empty the cart — `CheckoutService::completePayment()` calls it and then deletes the buyer's `carts` rows; every confirmation path (webhook, success page, PayPhone return, API) goes through it.
6. The gateway logic is shared by the web controllers and the API in `App\Services\Payments\StripeCheckout` (`intentFor()` — reuse/update/create the PaymentIntent, `PaymentInProgressException` in `processing|succeeded|requires_capture`; `verify()` — the no-webhook confirmation) and `PayPhoneCheckout` (`start()`, `confirm()` → `paid|canceled|error|mismatch|unknown`). The `clientTransactionId` carries the origin: `GS{id}-…` web, `GA{id}-…` app. The PayPhone return URL is the same for both; for a `GA` transaction it confirms and then redirects to `config('api.app_payment_return_url')` (`API_APP_PAYMENT_RETURN_URL`, default `mitienda://payment-result`) `?status=…&order=…`, which the app's in-app browser intercepts; its `cancellationUrl` is `payments.payphone.app-cancel`. The app can also confirm itself through the API. Seller order lists (`Seller\OrderController`) read from these notifications plus `order_details.seller_id`. `payment_gateway` is `stripe` or `payphone` (older rows may still say `kushki`).

Keys live in `config/services.php` (see its header comment for the expected `.env` vars): `STRIPE_*` and `PAYPHONE_TOKEN` / `PAYPHONE_STORE_ID`. PayPhone has a single API host; whether a token is test or live is decided by the application it belongs to in PayPhone Developer, and in production the button only works on the HTTPS domain registered there. After editing `.env`, run `php artisan config:clear`.

Note: `app/Contracts/PaymentGateway.php` defines an interface but nothing implements it yet; the two payment controllers are independent implementations. Kushki, the previous Ecuador gateway, was removed (it never had a checkout UI — only an endpoint).

### Product Variants (size & color)

Variants are **rows in `product_stocks`**, one per combination, with its own `size`, `color`, `price` and `qty`. `ProductStock::buildVariant($size, $color)` builds the key the cart speaks (`"40-negro"`, `"M"`, `"negro"`, or `''` for a flat product) and a `saving` hook keeps the denormalized `variant` column in sync, so the string is never composed by hand. Cart entries store that key in `carts.variation`. `products.variant_product` is a derived flag (`syncStocks()` recomputes it), not an input.

The JSON columns `choice_options` / `colors` / `variations` are **legacy**, still on the table and still read by `legacy:restore`'s double-encoding repair, but nothing in the live flow uses them. The product page is `pages/product-detail.blade.php` (`ProductController@show`); the old `pages/show.blade.php`, which classified sizes by guessing at the variant string, is deleted — no controller returned it and it had stopped rendering anyway, asking for `route('products.variant_price')`, a name that never existed.

`config/variants.php` is the single source for both the color palette and the size sets:

- `types` — each entry has `sizes` and a `size_label` (`apparel`, `waist`, `footwear`, `headwear`, plus `none`). Adding a size set needs no migration.
- `colors` — key (what `product_stocks.color` stores) → label + hex.
- `category_types` — category slug → type. Applied by `Category::applyConfiguredVariantTypes()`, called from the migration **and from `legacy:restore`**: `categories.variant_type` defaults to `'none'` and every repopulation brings it back that way, so the assignment has to be re-appliable rather than a one-shot `UPDATE`. (The original migration did it once, against a table that was still empty because the schema was migrated before the rows were restored — which left all 10 categories on `'none'` and no product able to offer a size.)

Which sizes a product offers is resolved by `Product::sizeOptions()` / `sizeLabel()` / `usesSizes()`: **`products.variant_type` wins, and the category's applies when it is null.** The per-product override exists because the catalog's categories are mixed — sneakers hang off "Sports & outdoor" next to tents — so the type cannot be decided per category without offering shoe sizes to half the shop. An unknown type falls back to the category, the same way an unknown category type falls back to "color only".

**Price.** `Product::finalPrice(?float $base)` is the only discount rule (percent or amount, never below 0): the cart (`CartController@add`), the product page, the quick-add modal, the listings, `discounted_price` and the API all call it — the same formula used to be copied in seven places, and the cart could go negative with a fixed discount. `Product::stockMap()` gives each combination `{qty, price, original_price}` where **`price` is the charged price** (discount applied): before, both pickers showed the raw row price after choosing a combination, higher than what the cart then charged.

Going the other way — turning the stored key back into something a person reads — is `ProductStock::parseVariant()` / `describeVariant()`, the inverse of `buildVariant()`. `describeVariant($key, $product)` returns the size with its label, the color with its palette name and hex, and a `text` fallback (`"Talla US 9 · Negro"`). `Cart` and `OrderDetail` reach it through the `DescribesVariant` trait (`variant_parts`, `variant_label`, `hasVariant()`), and every screen renders it via `partials/variant-badge.blade.php` — cart, mini-cart, checkout, payment success, `/orders`, the order detail, `/seller/orders` and `/admin/warehouse`. **Never print `variation` directly**; it is an internal key. A one-part key is ambiguous (`"M"` is a size, `"negro"` a color), so it is resolved against `config('variants.colors')`, and the size label needs the product *and its category*, which is why those views eager-load `product.category`.

Buyers pick a combination in two places, and both are the same picker at different sizes, fed by `Product::stockMap()` (combination → `{qty, price}`) so neither can offer a combination the other has dropped: the full product page (`pages/product-detail.blade.php`) and the quick-add modal the product card opens (`partials/quick-add-modal.blade.php`, served already rendered by `CartController@modal`, behavior in `layouts/app.blade.php` delegated on `#qa-root`). The modal used to return JSON while the JS injected it with `.html()`, so it dumped raw JSON on screen and the grid had no way to choose a size at all. `CartController` is `auth`-wide, so the modal bails out to login for guests rather than injecting the login page into itself. Both pickers price combinations client-side from the stock map, so there is no per-selection round trip; `ProductController@variantPrice` / `product.variant_price`, which served that purpose, is deleted.

The seller and warehouse tables list the order's lines through `partials/order-items-cell.blade.php`: neither showed them before, only the order total, so whoever picked the box had no way to know which size to pull. Covered by `tests/Feature/VariantVisibilityTest.php`.

`ProductService::validate()` enforces this server-side by resolving through a throwaway `Product` carrying the submitted `variant_type` plus the category, so the rule cannot drift from the sizes the form just rendered. The seller picks the type in `partials/variant-builder.blade.php` (shared by create and edit), which also builds the size × color stock matrix; the bulk CSV import accepts a `variant_type` column.

### Categories

The root categories are a fixed catalog in `config/categories.php` (35 Spanish categories, in menu order). `Category::syncCatalog()` applies it: a category whose old slug is listed under `legacy` is **renamed in place** (same id, image and products — the 10 original English categories became e.g. `womens-fashion` → `ropa-de-mujer`, `electronics` → `tecnologia`), missing ones are created, roots not in the catalog are kept but pushed to the end, and it finishes with `applyConfiguredVariantTypes()` (the slugs' size types are in `config/variants.php`). All panels are rendered at once and switched client-side; `?c=<slug>` picks the open one. "Destacados" is the first tab but **not** a category row (sellers must not file products under it): it shows `featured` products, falling back to best sellers. ### Seller Earnings & Settlements

The seller dashboard's "Ventas Totales" / "Ganancias Totales" are **per settlement cycle**, not all-time. A sale counts only once its line is **paid and delivered** (`order_details.payment_status = 'paid'` and `delivery_status = 'delivered'` — the warehouse's deliver action stamps the lines), and it stays in the cycle until an admin settles it (`order_details.settlement_id` is null). `OrderDetail::scopeSettleable()` is the one definition; a paid-but-undelivered order shows nowhere and cannot be settled, so a return or a lost parcel never gets paid out. Profits are sales minus the marketplace commission, `config('app.seller_commission_rate')` (0.25); the card shows the rate so the seller knows why the two numbers differ. "Pedidos Exitosos" is still an all-time count.

`app/Services/SettlementService.php` owns the whole thing: `pendingFor($sellerId)` / `pendingForAll()` compute the `{total_sales, commission, net_amount, lines_count}` breakdown — the dashboard and the admin panel both read it, so the figure the seller sees is exactly the one the admin pays — and `settle($seller, $admin)` closes the cycle. It creates a `SellerSettlement` row (the payout record: gross, rate, commission, net, who settled), stamps `settlement_id` on the lines and **credits the net to `users.balance`** — the seller's wallet, the same mechanism as an approved recharge, so they withdraw it through the existing `/wallet` withdrawal flow — all inside one transaction, locking the rows rather than an aggregate (PostgreSQL refuses `FOR UPDATE` on aggregates), so two admins cannot pay the same sales twice; with nothing pending it returns null and nothing is written. After the commit it sends `SellerSettledNotification` (`database` + `mail`, like the shop decision — the seller need not be online) outside the transaction, so a mail failure cannot roll back a credit that already happened. `DashboardController` reads the unread `database` copies, marks them read and passes `$settlementUpdates` to both dashboard views, which render `partials/settlement-banner.blade.php` — the same read-once pattern as `$shopUpdates`. Lines never get re-opened: a settlement is final. `/wallet` lists the seller's credited settlements above the recharge history (hidden when there are none).

**Every withdrawal waits for the admin**, settled money included (until 2026-11 a withdrawal covered by settlements was auto-approved; the owner decided all of them must be reviewed). `WalletService::requestWithdrawal()` deducts the amount at request time inside a transaction that locks the user row, always creates it `pending`, and approving only changes the status (the admin transfers the money outside the system); rejecting refunds the full amount and is only possible while pending, so nothing moves twice. `SettlementService::withdrawableFor($user)` (credited net − non-rejected `from_settlement` withdrawals, capped at the balance) now only feeds the informative `wallet_withdrawals.from_settlement` flag (`2026_09_18_150000_add_from_settlement_to_wallet_withdrawals.php`), which `/admin/wallet` shows as a "Liquidación" badge to help the decision. The wallet page no longer advertises instant withdrawals.

The admin panel is `/admin/settlements` (`Admin\SettlementController`, view `admin/settlements.blade.php`, under the `admin` route group): one row per seller with pending sales, commission, net, last settlement and a "Liquidar" button (`POST /admin/settlements/{seller}`, disabled at zero), plus the paginated payout history. The panel nav links it. The seller dashboard shows the date and amount of the last settlement under the stat cards (`$lastSettlement`). Covered by `tests/Feature/SellerSettlementTest.php`.

### Delivery / Warehouse Flow

After payment, `orders.delivery_status` advances (all four steps in `App\Services\OrderFulfillmentService`, the controllers only authorize and show the result): `pending` → `confirmed` (seller, `Seller\OrderController@confirm`) → `warehouse` (seller, `Seller\OrderController@sendToWarehouse`) → `on_the_way` (warehouse panel dispatch) → `delivered`. Each step stamps its timestamp (`confirmed_at`, `warehouse_at`, `dispatched_at` + `dispatched_by`, `delivered_at`) and every transition is guarded by a check on the previous status.

The warehouse panel (`/admin/warehouse`, `Admin\WarehouseController`, view `admin/warehouse.blade.php`) is **admin-only** (it lives in the admin route group, behind `admin` + `admin.2fa`) — it lists every seller's orders together with buyer contact data, so sellers must not reach it; they work from `/seller/orders`. It drives dispatch (`POST /admin/warehouse/orders/{id}/dispatch`) and delivery (`.../deliver`). Notifications (all `database` channel): `OrderArrivedWarehouseNotification` goes to all admins when a seller sends an order to the warehouse (shown as "nuevas llegadas" in the panel, marked read on view); `OrderStatusUpdatedNotification` goes to the customer on every status change (shown as a banner in `/orders`, marked read on view). The customer-facing tracker with step dates lives in `pages/order-detail.blade.php`. Full flow covered by `tests/Feature/WarehouseFlowTest.php`.

### Shared Business Services

Business rules live in `app/Services`, not in controllers, so the storefront, the seller panel, the admin panel and the future API run the same code. Controllers authorize (policies), call the service, and turn the result into a response.

- `ShopApprovalService` — approve/reject a shop (`Shop::PENDING|APPROVED|REJECTED`), audit, notify; a no-op returns `false`.
- `WalletService` — `requestRecharge`, `requestWithdrawal` (throws a `ValidationException` on `amount` when the balance is short), `approveRecharge` / `rejectRecharge` / `approveWithdrawal` / `rejectWithdrawal`.
- `OrderFulfillmentService` — `confirm` and `sendToWarehouse` (seller), `dispatch` and `deliver` (an `Admin`).
- `CartService` — `add`, `setQuantity`, `items`, `clear` (see **Mobile API**).
- `ProductService` — `validate($input, creating:)`, `create`, `update`, `setApproved` (moderation), `uniqueSlug`. It owns the size × color rules that used to be private to `Seller\ProductController`; the CSV import keeps its per-row rules and shares only `uniqueSlug`.
- `SettlementService`, `CheckoutService` — as described in their sections.

When a step does not apply in the current state, a service throws `App\Exceptions\BusinessRuleException` with a translated, user-facing message (web controllers flash it; an API would answer 422 with it). Every state change that moves money or an order (`approveRecharge`, `rejectWithdrawal`, each fulfillment step…) runs in a transaction that **re-reads the row with `lockForUpdate()`** before checking its state, so a double click or two admins cannot credit, refund or advance twice — before this a doubled "approve recharge" could credit the balance twice. Notifications go out after the commit. Covered by `tests/Feature/AdminOrdersTest.php`.

### Admin Catalog Moderation & Orders

`/admin/products` (`Admin\ProductController`, views `admin/products/*`): list with search, shop and status filters (on sale / disabled by moderation / unpublished by its seller), product page with stock per combination, edit, approve and disable. **`published` belongs to the seller and `approved` to the panel**; the shop shows a product only when both are 1 (`Product::scopeActive()`), and the seller's list marks a disabled product "Desactivado por moderación". Editing uses **the seller's form**, `partials/product-form.blade.php` (taking `$formAction` and `$cancelUrl`; `pages/seller-product-edit` includes it too) and `ProductService`, so the panel cannot save a combination the seller form would reject; the owner (`added_by`) never changes.

Every storefront product query goes through `->active()` — home, search, brands, `/products`, the product page, related products, `/categories` and `/category/{slug}` (the last three used to check only `published`, so a disabled product stayed reachable) — and `CartController@add` / `@modal` use `Product::active()->findOrFail()`, so a disabled or unpublished product cannot be added to a cart (404). Lines already in a cart are not removed.

`/admin/orders` (`Admin\OrderController`, views `admin/orders/*`) lists every order with code, payment, delivery and date filters, and shows any order with buyer contact, lines per shop with variant badge, settlement mark, payment reference and the step dates. It is read-only: the warehouse moves orders. This replaced the old storefront power of `user_type = 'admin'` to open any `/orders/{id}`; `pages/order-detail` now shows full buyer data only to the order's seller. Covered by `tests/Feature/AdminProductModerationTest.php` and `tests/Feature/AdminOrdersTest.php`.

### Frontend

Tailwind CSS v4 via Vite plugin. No Vue/React — plain ES modules in `resources/js/`. Blade layouts in `resources/views/layouts/`, partials heavily used via `@include`.

Note: much of the page JS (language/currency switchers, search autocomplete) lives inline in `resources/views/layouts/app.blade.php`, not in `resources/js/` — search both when hunting for a handler.

**Mobile.** Tailwind is *not* loaded by the storefront layout — only the theme's Bootstrap 4 CSS (`public/assets/css/`) — so a Tailwind class such as `min-w-0` silently does nothing there (it once hid the mini-cart's remove button). Before hiding anything below a breakpoint (`d-none d-lg-block`), make sure the phone has another way to it: that pattern hid "Cerrar sesión" and the header cart. Hover-only UI is unreachable on touch screens: the product-card icons (wishlist, compare, quick-add) are revealed only on `:hover` by the theme, so the layout shows them permanently under `@media (hover: none), (max-width: 991.98px)`.

**Search.** Every product text search goes through `Product::scopeSearch($term, $columns = ['name'])`: case-insensitive via `LOWER()` on both sides (PostgreSQL's `LIKE` is case-sensitive, so `where('name', 'like', …)` missed "Zapatillas" for "zapa"; SQLite ignores ASCII case, which is why tests never caught it) and with the user's `%`/`_` escaped. The header autocomplete posts `search` to `POST /ajax-search` (`SearchController@ajax`), which answers `partials/search-suggestions.blade.php` already rendered, or `'0'` for no results — the JS injects it with `.html()`, so it must not return JSON. The JS debounces 250 ms and drops responses for text no longer in the field. Covered by `tests/Feature/SearchTest.php`.

### Storefront Rate Limits

`AppServiceProvider::configureStorefrontRateLimiting()` defines `search` (60/min per IP, on `POST /ajax-search`), `cart` (120/min per user, the whole `/cart*` group — the mini-cart reloads on every page, hence the headroom) and `checkout` (30/min per user, `GET /checkout` + `POST /checkout/shipping`, since each visit creates or syncs the pending order). `checkout.success` and the webhooks are deliberately left out. Most callers are AJAX — jQuery or `fetch` without AJAX headers — so the 429 is chosen **by route, not by header**: JSON `{status: 'error', message}` everywhere except the two full pages, `GET /cart` and `GET /checkout`, which render `errors/429.blade.php` (also Laravel's default page for any other 429). The JS shows that `message`: the search box stops its spinner and says it, the mini-cart ignores the error instead of printing `undefined`, add/remove/quantity show it as a toast. Covered by `tests/Feature/StorefrontThrottleTest.php`.

The public forms have their own limiters in `configureAccountRateLimiting()`: `login` (5/min per email+IP, 20/min per IP — same shape as `admin-login`), `register` (5/min and 20/hour per IP), `shop-register` on `POST /shops/create` (3/min and 10/hour per IP: each submission creates a user and uploads ID documents) and `subscribe` (5/min and 30/hour per IP). They are classic forms, so a hit goes `back()` with the input (never the password; uploaded files are dropped by Laravel) and the warning as an `email` error, which those views already render; the newsletter form lives in the footer, which renders no errors, so it uses the global `error` flash. A JSON request gets a JSON 429 instead. Covered by `tests/Feature/AccountThrottleTest.php`. The `GET` pages are not throttled.

### Localization

Default locale is `es` (`config/app.php` + `.env`). The topbar switcher POSTs to `/language` (`LanguageController@change`, param name `locale`), which stores `session('locale')`; `SetLocale` middleware applies it on every `web` request. Supported locales are declared once in `SetLocale::SUPPORTED` — the topbar dropdown and the controller both read from it, so adding a language means adding it there plus a `lang/<code>/` directory.

Every user-facing string goes through `__()`. Two conventions coexist, and which one applies depends on where the string lives:

- **Spanish string keys + `lang/en.json`** for views, controller flash/JSON/abort messages, notifications rendered in views and the labels in `config/variants.php`: write the Spanish text as the key (`__('Añadir al carrito')`, placeholders as `:name`) and add its English line to `lang/en.json`. Spanish needs no file — the key is the fallback. `tests/Feature/LocalizationTest.php` scans every Blade file and fails when a key is missing from `en.json`, so add the translation in the same change.
- **PHP array files** (`lang/es|en/*.php`) for the framework's own strings — `validation.php` (with the form field names under `attributes`, in both languages: the fallback locale is `es`, so an `en` gap would surface Spanish field names inside English sentences), `auth.php`, `pagination.php`, `passwords.php` — plus the older `dashboard.php` / `topbar.php` keys the dashboards and topbar still use.

Order and payment statuses are never printed raw: `delivery_status_label()` / `payment_status_label()` in `app/Helpers/helpers.php` map the stored keys through `__()` (before that, the views did `ucwords(str_replace('_', ' ', …))` and showed "On The Way" in a Spanish store). The size/color labels in `config/variants.php` stay Spanish in the file and are translated where they are read (`Product::sizeLabel()`, `Category::sizeLabel()`, `ProductStock::describeVariant()`, the two variant pickers, the variant builder), so `describeVariant()` already returns the localized label.

What is deliberately **not** translated: the legal prose in `pages/policy.blade.php` (content the owner must vet, not UI — the page shows a "Spanish only" notice under other locales), and the mail notifications, which are sent in the app's default locale because users have no stored language preference (`HasLocalePreference` would be the hook if one is added).

The dashboard sidebars (`pages/dashboard-verified`, `pages/dashboard-index`) only link to features that exist: the refund, wholesale, coupon, classified, reviews and downloads entries were `href="#"` placeholders inherited from the theme with no backend behind them (`Review` is a model with no routes or UI) and were removed together with their `dashboard.nav.*` keys; "Soporte" goes to the support-policy page. The old "Visitantes de Hoy" card, hard-wired to 0, is now "Pedidos por Confirmar" (`$stats['pending_orders']`: paid orders with a line of the seller still `delivery_status = 'pending'`), linking to `/seller/orders?delivery_status=pending`. `tests/Feature/SellerDashboardTest.php` fails if a `href="#"` comes back into either sidebar.

### Queue & Sessions

Both queue driver and session driver are set to `database` (see `.env`). Run `php artisan queue:listen` during development or queue jobs will not process. Tests override to `sync`/`array` in `phpunit.xml`.

### Tax

Ecuador IVA rate (15%) is read from `config/app.php` (key: `ec_iva_rate`). `PayPhoneService::amounts()` back-calculates the IVA base from the order total, which already includes it (PayPhone requires `amountWithTax` + `tax`, in cents, and the three parts must add up to `amount`); an optional `services.payphone.iva_rate` config overrides the rate.

## Database Notes

- Tests use in-memory SQLite (configured in `phpunit.xml`); local/production uses PostgreSQL (migrated from MySQL 2026-07; the old XAMPP MySQL `woot_db` is kept as a backup — it holds the only copy of the seed data, see `legacy:restore` below). PostgreSQL runs as a Windows service independent of XAMPP.
- `database/migrations/` has 31 migration files — always run `php artisan migrate` after pulling changes. `orders`/`order_details` come from `2026_06_10_200000_create_orders_table.php`; database notifications from `2026_06_22_184700_create_notifications_table.php`; `seller_settlements` + `order_details.settlement_id` from `2026_09_18_120000_create_seller_settlements_table.php`; `admin_two_factors` and `admin_audit_logs` from the two `2026_10_27_*` migrations; `admins` from `2026_11_04_120000_create_admins_table.php`, which also repoints `seller_settlements.admin_id`, `orders.dispatched_by` and `admin_two_factors` (`user_id` → `admin_id`) to `admins`, adds `admin_audit_logs.admin_id` and moves the admins' notifications to `notifiable_type = Admin`. It copies each admin with the same id, so the values do not change; it aborts if one of those columns points at a non-admin, and `down()` restores everything through `legacy_user_id` (verified against PostgreSQL).
- File uploads go to `storage/app/public/`; the `public/storage` symlink must exist (`php artisan storage:link`).

### Image Uploads (`ImageOptimizer`)

Every user upload goes through `app/Services/ImageOptimizer.php` — `$images->store($file, $dir, $profile)` instead of `$file->store($dir, 'public')`, returning the same disk-relative path. The five call sites: product thumbnail and photos (`Seller\ProductController` store/update), avatar (`ProfileController`), shop ID documents (`Seller\RegistrationController`) and recharge proofs (`WalletController`). **New upload points should use it too.**

Per profile in `config/images.php` (`max` px on the long side + `quality`), it applies the EXIF orientation of phone photos (re-encoding drops EXIF, so the rotation must land in the pixels), downscales, and re-encodes to WebP keeping transparency. It keeps the original file when re-encoding would not shrink an image that needed no resize or rotation, and stores anything that is not JPEG/PNG/WebP (PDF proofs, GIFs, animated WebP) untouched, as it does on any processing error. On the existing catalog this took 6.4 MB down to 2.3 MB.

It needs the **GD** extension. XAMPP ships it disabled: `extension=gd` in `C:\xampp\php\php.ini` (enabled 2026-10-01; that file is CRLF — edit it with something that keeps line endings, since Git Bash's `sed -i` silently rewrites every line to LF), then restart `php artisan serve` / Apache. Without GD, or with `IMAGE_OPTIMIZE=false`, uploads are stored as-is — nothing breaks, they are just heavy. Covered by `tests/Feature/ImageOptimizerTest.php` (skipped without GD).

The per-file upload limit is `images.max_upload_kb` (8192 KB, `IMAGE_MAX_UPLOAD_KB`), read by all five validations and by the hint under each file input — never hard-code a `max:` for an image upload. It can be generous because only the reduced copy is kept; it was 2–3 MB before and rejected an ordinary phone photo. PHP must let it through first: `upload_max_filesize` ≥ the limit, and `post_max_size` ≥ 6 × the limit for the product form (thumbnail + 5 photos) — XAMPP's `php.ini` was raised to `post_max_size=64M` on 2026-10-01; behind nginx, `client_max_body_size` too. Running out of `memory_limit` is a fatal error no `catch` can stop, so `ImageOptimizer::fitsInMemory()` estimates 9 bytes per pixel before decoding and stores the original when it would not fit.

Images uploaded before the optimizer existed are converted by `php artisan images:optimize` (`app/Console/Commands/OptimizeStoredImages.php`; `--pretend` shows the per-file savings and writes nothing, `--force` skips the prompt, `--keep-originals` leaves the old files on disk). It only touches files referenced from the columns in its `COLUMNS` map — each mapped to a profile, so banners, category images and brand logos have profiles in `config/images.php` too — and leaves orphans alone; a file shared by two columns gets the more generous profile. For each file it writes the new one, repoints every referencing row (including the `products.photos` JSON) in a transaction, and only then deletes the original, so a failed update never leaves a row pointing at nothing. It is idempotent: a WebP already within its profile is skipped, since re-encoding it every run would only stack quality loss.

The converted file **keeps its name and changes only the extension** (`cat-sports.jpg` → `cat-sports.webp`), and it refuses to overwrite an existing file with that name. That is what keeps `legacy:restore` working afterwards: restored rows carry the old `.jpg` paths, and its `repairImageExtensions()` repoints them to the same name under another extension — which is why that repair now also walks the `products.photos` arrays. Covered by `tests/Feature/OptimizeStoredImagesTest.php`.

### Restoring Seed Data (`legacy:restore`)

The 2026-07 MySQL → PostgreSQL migration created the schema but **never moved the rows**. An empty `banners`/`categories`/`brands`/`products` makes the home page render with no images at all — the `@foreach` loops just iterate empty collections, so the symptom looks like broken image paths when it is actually missing data. `php artisan migrate:fresh` reproduces the same empty state.

`php artisan legacy:restore` (`app/Console/Commands/RestoreLegacyData.php`) repopulates from the old XAMPP MySQL `woot_db`, which is still the only copy of that data:

```bash
php artisan legacy:restore --pretend   # show what it would do, write nothing
php artisan legacy:restore --force     # skip the confirmation prompt
```

Options: `--host` / `--port` / `--database` / `--username` / `--password` (default to the XAMPP MySQL `woot_db`), `--tables=a,b` to limit the run, `--with-notifications` to include `notifications` (skipped by default — the legacy rows point at orders that no longer exist).

It only ever reads from the source, and it is idempotent: any table that already has rows is skipped, so re-running is safe. It copies the intersection of columns (the two schemas differ by a few newer nullable columns), walks 19 tables in dependency order, and resyncs the PostgreSQL identity sequences afterwards — skip that last step and the next insert collides on a duplicate id.

**Users get special handling.** A local account may be newer than the legacy one but share its email, and the unique email index means they cannot both exist. In that case the local row wins — keeping its password — and only adopts the legacy `id` and `user_type`, so `products.added_by` and the other FKs still line up.

It also repairs two defects that predate the migration: values whose JSON was encoded twice (with the model's `'array'` cast those decode to a string instead of an array, so the product gallery renders nothing), and rows whose image is missing from disk but present under another extension. It finishes by listing any referenced image that is still missing.

**MySQL must be running**, and it is not a Windows service — start it from the XAMPP control panel, or `mysqld.exe --defaults-file=C:\xampp\mysql\bin\my.ini --standalone`. If it aborts with `Failed to initialize multi master structures`, the data dir has corrupt replication state: `mysqld` log output was once written into `multi-master.info`, so MariaDB reads each log line as a named replica. Move `master-*.info`, `relay-log*.info`, `mysql-relay-bin-*` and `multi-master.info` out of `C:\xampp\mysql\data\` — they hold no table data (a set from 2026-07 is parked in `data\_repl_backup_20260824\`).

The command restores data as it exists in the backup, and nothing more: shops come back with their original `status` (`0` pending) and users with their original verification state. Approving a shop and verifying an email are separate actions.
