# API v1 — apps móviles (compradores y vendedores)

Base: `https://<tu-dominio>/api/v1` (en local, `http://127.0.0.1:8000/api/v1`).

Solo para **compradores y vendedores** (`users`). El panel de administración no
tiene endpoints aquí ni los tendrá: si algún día necesita API será otra
(`/admin-api`) con su propio guard. `tests/Feature/Api/V1/ApiRoutesTest.php`
falla si una ruta de `/api` toca el panel.

> Estado: **2a — autenticación**. Catálogo (2b), carrito, checkout y pagos
> (2c), perfil y endpoints de vendedor (2d) y la especificación OpenAPI (2e)
> llegan en las siguientes sub-fases.

## Convenciones

**Cabeceras de cada petición**

| Cabecera | Valor |
|---|---|
| `Accept` | `application/json` (recomendado; la API responde JSON aunque falte) |
| `Content-Type` | `application/json` en los POST con cuerpo |
| `Authorization` | `Bearer <token>` en los endpoints con 🔒 |
| `Accept-Language` | `es` (por defecto) o `en`. Los mensajes `message` salen en ese idioma; la respuesta trae `Content-Language`. |

**Respuestas correctas**

- Un recurso: `{ "data": { ... } }`
- Una lista: `{ "data": [ ... ] }` (paginadas: además `links` y `meta`, desde 2b)
- Una acción sin recurso: `{ "message": "..." }` con 202, o `204` sin cuerpo.

**Errores** — siempre el mismo formato:

```json
{ "message": "Texto para mostrar al usuario", "code": "codigo_estable" }
```

Las validaciones añaden `errors` por campo:

```json
{
  "message": "Los datos enviados no son válidos.",
  "code": "validation_failed",
  "errors": { "email": ["El campo correo electrónico es obligatorio."] }
}
```

La app debe decidir por **`code`**, nunca por el texto (va traducido).

| HTTP | `code` | Cuándo |
|---|---|---|
| 401 | `unauthenticated` | Sin token, token revocado o **caducado** → ir al login |
| 401 | `invalid_credentials` | Login con correo o contraseña incorrectos |
| 403 | `email_not_verified` | Login de una cuenta sin verificar → ofrecer reenviar el correo |
| 403 | `account_disabled` | Cuenta bloqueada (también si se bloquea con la sesión abierta: el token se revoca) |
| 403 | `forbidden` | El token no tiene la habilidad necesaria |
| 404 | `not_found` | Ruta o recurso inexistente (o ajeno: nunca se confirma que existe) |
| 405 | `method_not_allowed` | Verbo HTTP incorrecto |
| 422 | `validation_failed` | Datos inválidos; ver `errors` |
| 422 | `business_rule` | La operación no procede en el estado actual (p. ej. un pedido que no está en el paso anterior) |
| 429 | `too_many_requests` | Límite de peticiones; esperar `Retry-After` segundos |

**Límites**

| Grupo | Límite |
|---|---|
| Toda la API | 60 peticiones/min por usuario (o por IP sin token) |
| `register`, `login`, `email/resend`, `password/forgot` | 5/min por correo+IP y 20/min por IP |

## Sesiones por dispositivo

- Cada login crea un **token por dispositivo**. La app genera un `device_id`
  estable al instalarse (un UUID guardado en almacenamiento seguro) y lo manda
  siempre: volver a entrar desde el mismo dispositivo **reemplaza** su token.
- Los tokens **caducan** a los 30 días (`API_TOKEN_TTL_DAYS`). La app debe
  **rotarlo** (`POST /auth/token/rotate`) al abrirse si quedan menos de ~7 días
  para `expires_at`: así una sesión en uso no caduca nunca y un móvil
  olvidado se cierra solo.
- Como mucho 10 dispositivos por cuenta (`API_MAX_DEVICES`); al pasarse, el
  login cierra la sesión menos usada.
- El usuario ve sus sesiones y puede cerrar cualquiera (`/auth/devices`).
- Guarda el token en **almacenamiento seguro** (Keychain / Keystore, p. ej.
  `flutter_secure_storage`), nunca en preferencias planas. En la base solo
  queda su hash.

**Habilidades (abilities)** del token según el rol:

| Rol | Habilidades |
|---|---|
| Comprador (y vendedor sin tienda aprobada) | `profile:read`, `profile:write`, `cart:write`, `checkout:write`, `orders:read` |
| Vendedor con tienda aprobada | lo anterior + `seller:products`, `seller:orders` |

Se calculan al emitir o rotar el token: si un vendedor recibe la aprobación de
su tienda, obtiene las de vendedor en su siguiente rotación. Ningún token tiene
habilidades de administración.

## Endpoints

### `POST /auth/register`

Alta de **comprador**. No devuelve token: hay que verificar el correo (el
enlace del email abre la web) y luego hacer login.

```json
{ "name": "Ana Pérez", "email": "ana@correo.com",
  "password": "Clave1234", "password_confirmation": "Clave1234",
  "phone": "+593 99 999 9999" }
```

Contraseña: mínimo 8 caracteres con letras y números. Cualquier otro campo
(`user_type`, `balance`…) se ignora.

`201`:

```json
{ "data": { "id": 7, "name": "Ana Pérez", "email": "ana@correo.com", "phone": "+593 99 999 9999",
            "avatar_url": null, "type": "customer", "email_verified": false, "balance": 0,
            "shop": null, "created_at": "2026-11-05T10:00:00-05:00" },
  "message": "Cuenta creada. Te enviamos un enlace para verificar tu correo; después podrás iniciar sesión." }
```

Errores: `422 validation_failed` (correo repetido, contraseña débil…).

### `POST /auth/login`

```json
{ "email": "ana@correo.com", "password": "Clave1234",
  "device_id": "3f2a9c1e-5b7d-4e8f-9a0b-1c2d3e4f5a6b", "device_name": "Pixel 8 de Ana" }
```

`device_id`: letras, números y `. _ : -`, máx. 100. `200`:

```json
{ "data": {
    "token": "12|Qm9n…",
    "token_type": "Bearer",
    "expires_at": "2026-12-05T10:00:00-05:00",
    "abilities": ["profile:read", "profile:write", "cart:write", "checkout:write", "orders:read"],
    "device": { "id": 12, "device_id": "3f2a9c1e-…", "device_name": "Pixel 8 de Ana" },
    "user": { "id": 7, "name": "Ana Pérez", "type": "customer", "...": "..." } } }
```

Errores: `401 invalid_credentials` (igual exista o no el correo),
`403 email_not_verified`, `403 account_disabled`, `429 too_many_requests`.

### `GET /auth/me` 🔒 `profile:read`

El usuario del token. `meta.abilities` lista las habilidades del token actual.

### `POST /auth/token/rotate` 🔒

Sin cuerpo. Devuelve un token nuevo (mismo formato que el login) para el mismo
dispositivo, con la caducidad renovada y las habilidades recalculadas. **El
token anterior deja de valer en el acto**: guarda el nuevo antes de hacer otra
petición.

### `POST /auth/logout` 🔒

Revoca el token de este dispositivo. `204`.

### `GET /auth/devices` 🔒

```json
{ "data": [
  { "id": 12, "device_id": "3f2a…", "device_name": "Pixel 8 de Ana", "abilities": ["..."],
    "current": true, "last_used_at": "2026-11-05T10:05:00-05:00",
    "created_at": "2026-11-05T10:00:00-05:00", "expires_at": "2026-12-05T10:00:00-05:00" } ] }
```

Nunca incluye el token.

### `DELETE /auth/devices/{id}` 🔒

Cierra la sesión de ese dispositivo (un `id` de la lista). `204`; `404` si no
es de esta cuenta.

### `DELETE /auth/devices` 🔒

Cierra **todas las demás** sesiones. Con `?include_current=1`, también esta.
`204`.

### `POST /auth/email/resend`

`{ "email": "ana@correo.com" }` → `202` con el mismo mensaje exista o no la
cuenta.

### `POST /auth/password/forgot`

`{ "email": "ana@correo.com" }` → `202` con el mismo mensaje exista o no la
cuenta. El enlace del correo abre la web para elegir la contraseña nueva. Si se
pide dos veces en menos de 60 s: `429 too_many_requests`.

## Notas para Flutter

- **Cliente HTTP**: un interceptor (p. ej. `dio`) que añada `Authorization`,
  `Accept` y `Accept-Language`, y que ante `401 unauthenticated` borre el
  token y lleve al login.
- **Rotación**: al abrir la app, si `expires_at - ahora < 7 días`, llamar a
  `/auth/token/rotate` antes de nada y guardar el token nuevo.
- **Pagos** (sub-fase 2c): Stripe con su SDK nativo (`flutter_stripe`,
  PaymentSheet con el `client_secret` que dará la API). PayPhone no tiene SDK:
  se abrirá su URL de pago en un navegador in-app / Custom Tab y la vuelta
  llegará a la app por un deep link (App Links / Universal Links); el detalle
  irá en 2c.
